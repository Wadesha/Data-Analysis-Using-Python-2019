🎯 实战案例与最佳实践

从「会描述需求」到「能交付项目」· 6 个零基础可上手案例 + 7 条可复用的 Vibecoding 准则

怎么用本页：入门案例给你「照着做一遍」的最短路径，每个案例都标注了技术栈、耗时与可复用的枢纽资源； 最佳实践是你每次开新项目都应回看的检查清单。两者配合，避免「AI 生成了但跑不起来 / 上线即泄露」两类典型事故。

入门案例 零基础 · 30 分钟 ~ 2 小时可交付

🌟 个人作品集 / 博客 ~30 分钟

目标：用 AI 生成一个响应式个人站并部署到公网。

技术栈：Next.js (App Router) · Tailwind · Vercel · Cursor

步骤：① 用 Cursor 生成 Next.js 骨架 → ② 描述布局让 AI 填充组件 → ③ 接 AI 写作助手生成文章 → ④ vercel --prod 一键部署。

复用：模板「Next.js 模板」· API「Vercel 部署」

📚 RAG 知识库问答 ~1 小时

目标：上传文档，用自然语言提问得到基于文档的答案。

技术栈：Python · LangChain · OpenAI/Claude · 向量库 (Qdrant/Pinecone) · Streamlit

步骤：① 切分文档 + 向量化 → ② 建检索器 → ③ 拼「基于检索结果回答」的 Prompt → ④ 流式输出 → ⑤ 加 UI。

复用：AI 编码「RAG 模式」· 模型「LLM」· API「向量库」

📊 交互数据看板 ~45 分钟

目标：把一份 CSV 变成可筛选、可交互的仪表盘。

技术栈：Python · pandas · Streamlit · 本项目 13 个本地数据集

步骤：① 载入数据集 → ② 让 AI 写图表函数（柱/分布/缺失率）→ ③ 加筛选器与交互 → ④ 部署 Streamlit Cloud。

复用：数据集中心「13 本地含图表」· wine 示例

🔌 Chrome 插件（AI 总结） ~1 小时

目标：选中网页文字，一键调用 LLM 生成摘要 / 翻译。

技术栈：Manifest V3 · JavaScript · LLM API (OpenAI/DeepSeek)

步骤：① 写 manifest + content script 捕获选区 → ② 调 LLM API → ③ 弹窗 UI 展示 → ④ 本地加载 (chrome://extensions) 测试。

复用：API「LLM」· 智能体「Tool Use」

🤖 自动化周报 Agent ~2 小时

目标：自动汇总本周 Git/Issue 进展，生成结构化周报。

技术栈：n8n / CrewAI · GitHub API · LLM

步骤：① 连 GitHub API 拉取提交/PR → ② 设计「分析员 + 写手」多角色 Agent → ③ 拼周报模板 → ④ 定时触发（每周五）。

复用：智能体「CrewAI / 多 Agent」· API「GitHub」

💬 Telegram / Slack 机器人 ~1 小时

目标：用自然语言让机器人查数据 / 调 API / 发通知。

技术栈：Python · python-telegram-bot · LLM · 任意后端 API

步骤：① @BotFather 建 bot 拿 token → ② 写 message handler → ③ 接 LLM 理解意图 → ④ 部署 Railway（免费层）。

复用：API「Telegram / Slack」· 模型「LLM」

进阶案例 有基础后挑战 · 2–4 小时

🎯 微调自有客服模型 进阶

目标：通用 LLM 答不好你家业务术语，用领域数据定制一个小模型。

技术栈：Python · PEFT · TRL · Unsloth · DeepEval · 本项目 13 数据集之一作训练样本

步骤：① 整理问答对 SFT 数据 → ② Unsloth + LoRA 单卡训练 → ③ DeepEval 评测对比基线 → ④ 导出接推理。

复用：模板·微调案例 · 模型·微调工具链 · 数据集中心

🎨 多模态内容生成流水线 进阶

目标：输入一篇文章，自动产出配图 + 语音播报 + 短视频。

技术栈：GPT-4o Vision · SD/FLUX · OpenAI TTS · ffmpeg

步骤：① LLM 拆脚本/写画面描述 → ② 文生图(本地 ComfyUI 省钱) → ③ TTS 配音 → ④ ffmpeg 合成视频。

复用：模型·多模态案例 · API·语音转录案例

🗂 数据管线自动化 进阶

目标：每天把多源 CSV 自动清洗、关联、生成可交互看板。

技术栈：Python · Polars · DuckDB · Prefect · Streamlit · 本项目本地数据集

步骤：① Prefect 编排每日任务 → ② Polars 清洗 + DuckDB 聚合 → ③ Streamlit 渲染 → ④ 异常用 Great Expectations 告警。

复用：模板·ETL 案例 · 数据集中心 · 技术栈·实时看板

最佳实践 每次开新项目都应回看的检查清单

📋 规格驱动（Spec-first）

先写清楚「要做什么」（PRD / Spec / 用户故事），再让 AI 实现。结构化需求能显著降低 AI 幻觉与返工。

做法：用 GitHub Issue 或 spec-kit 把需求拆成可验证的小条目，逐条让 AI 交付并自查。

🎯 提示词工程原则

稳定的「角色 + 任务 + 约束 + 示例 + 输出格式」五段式；大任务拆小步、逐步验证，不要一次丢给 AI 一个巨型需求。

进阶：结构化输出（JSON Schema）、Few-shot 示例、Reflection 自检。详见 AI 编码「Prompt 模式」。

🔍 代码审查与测试

AI 生成 ≠ 正确。必做：① 人工审查关键逻辑 ② 让 AI 补单元测试 / E2E ③ 接 AI 审查工具（CodeRabbit / Snyk Code）兜底。

本项目对所有页面改动都跑 check_render.js 回归门禁——这就是「AI 写的也要测」的实证。

🔐 密钥与凭证安全（本项目实证）

凭证永不进代码 / 仓库：存 macOS 钥匙串（security add-internet-password），.gitignore 排除 .env、*.token；推送前确认。

教训：本项目曾因无防护把 GitHub token 推到仓库暴露——此后改为钥匙串 + 强 .gitignore 防护。

💰 成本控制

简单任务用小模型（Haiku / DeepSeek），复杂推理才上大模型；加缓存与批量调用，监控 token 用量避免隐形超支。

架构上做「成本感知路由」：按任务难度自动选模型，详见 模型中心「部署方式对比」。

🔄 版本控制与部署

小步提交、写清 commit message；合并前让 CI 跑校验；优先无服务器部署（Vercel / Railway / Cloud Run）降低运维负担。

本项目静态站可直接 GitHub Pages，但每次推送触发部署都需你确认，避免额度消耗与误暴露。

⚠️ 常见陷阱规避

① 盲信 AI 输出的版本号 / API 细节（务必查证）② 无测试就上线 ③ 把大文件 / 数据集 / 密钥入库 ④ 公开前未脱敏。

本项目原则：原始数据不入库（仅元数据 + 派生统计），可视化只用聚合值，从源头规避体积与版权风险。
